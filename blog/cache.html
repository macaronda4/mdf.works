HTMLは新しいのにCSSだけ古い
静的サイトのキャッシュの罠

パソコンでは問題なく、スマートフォンでだけレイアウトが崩れる。 アイコンが画面いっぱいに膨らみ、ボタンが未装飾になる。 原因は CSS の中身ではなく、HTML と CSS で「寿命」が違っていたことでした。

開発 2026年8月18日 約7分で読めます

目次

    起きたこと

    このサイトのブログ一覧に、検索窓とタグの絞り込みを追加した直後の話です。 パソコンでは意図どおりに表示されるのに、スマートフォンで開くと崩れていました。

    • 検索窓の虫眼鏡アイコンが、画面の横幅いっぱいに拡大されている
    • カテゴリのボタンが、装飾のない素のボタンに見える
    • 共有ボタンの X のロゴが、これも画面いっぱい

    アイコンが巨大化するのは、SVG に寸法指定がなく、CSS も当たっていないときの典型的な見た目です。 つまりスタイルが適用されていない。ここまでは分かります。 分からないのは、なぜパソコンでは正常なのか、です。

    最初に疑ったこと（と、外れた理由）

    真っ先に疑うのは CSS の書き間違いです。どこかに閉じ忘れの波括弧があると、 そこから後ろのルールがまとめて無効になります。実際そういう壊れ方は珍しくありません。

    ただ、それならパソコンでも同じように崩れるはずです。 端末によって CSS の解釈が変わるわけではありません。 仮説が症状を説明できていないので、これは違います。

    次に疑ったのはデプロイ漏れ。ファイルは書き換えたが、公開されているものは古いまま、という筋です。 これは症状と噛み合います。確かめるには、手元のファイルではなく、実際に配信されているものを見るのがいちばん早い。

    配信物を直接見る

    ブラウザの開発者ツールでも確認できますが、コマンドで取ってしまうほうが確実です。 ブラウザ自身のキャッシュが介在しないので、素の配信内容が分かります。

    見たいことやること
    配信中の CSS に、目的のルールが入っているかCSS を取得して、セレクタ名で検索する
    いつまでキャッシュされる設定かレスポンスヘッダの Cache-Control を見る
    圧縮が効いているかContent-Encoding を見る

    結果は拍子抜けするものでした。配信されている CSS には、追加したはずのルールが すべて含まれていたのです。デプロイは成功していました。

    原因：寿命の違う2つのファイル

    答えはレスポンスヘッダにありました。HTML と CSS で、キャッシュの設定がまったく違っていたのです。

    ファイルCache-Control意味
    HTMLmax-age=0, must-revalidate毎回サーバーに確認する。つまり常に最新
    CSSmax-age=8640024時間は確認せず、手元のものを使う

    前日にサイトを見ていた端末は、CSS を24時間ぶん抱えています。 そこへ翌日アクセスすると、HTML だけが新しくなり、CSS は昨日のままになる。 新しいマークアップに、そのマークアップを知らないスタイルシートが当たっていたわけです。

    パソコンで正常だったのは、単に「その端末では初めて開いたから」でした。 環境の違いではなく、訪問履歴の違いだったのです。 これに気づくまで、ブラウザの差異を疑って時間を使いました。

    この不具合のたちが悪いところ： 開発している本人はスーパーリロードを習慣的に使うので、まず遭遇しません。 遭遇するのは「前にも来たことがある訪問者」だけです。 しかもその人たちは、わざわざ報告してくれません。黙って離脱します。

    「キャッシュを消してください」は解決ではない

    その場しのぎとしては有効ですが、対処としては失格です。 訪問者にキャッシュ操作を求めるのは、こちらの設計不備を相手に押し付けているだけですし、 そもそも大半の人はやり方を知りません。

    直すべきは仕組みのほうです。方法は3つあります。

    案1：CSS のキャッシュ期間を短くする

    いちばん素直ですが、あまり良くありません。 期間を短くするほど問い合わせが増え、キャッシュの意味が薄れます。 かといって長くすれば同じ問題が起きる。どこに設定しても、どちらかが犠牲になります。 根本的には「同じ URL で中身が変わりうる」ことが問題なので、そこに手を入れないと解決しません。

    案2：URL に内容のハッシュを入れる

    /assets/site.css?v=94eb1160 のように、ファイルの中身から計算した値を URL に付けます。 中身を1文字でも変えればハッシュが変わり、別の URL になる。 古いキャッシュは参照されなくなり、確実に新しいものが読まれます。

    そのうえ、URL が変われば内容も必ず変わるので、 キャッシュ期間は逆に思い切り長くできます。1年でも構いません。 「短くする」のではなく「長くしても壊れないようにする」という発想の転換です。

    ビルドの手順にハッシュ計算を組み込む必要はありますが、 静的サイトなら小さなスクリプト1本で足ります。

    案3：CSS を HTML に埋め込む

    別ファイルにするのをやめて、<style> としてページに直接書いてしまう方法です。 HTML は毎回最新が配信されるので、CSS が HTML より古くなること自体が起こらなくなります。

    副次的に、描画をブロックする往復が1つ減るので表示も少し速くなります。 代わりに、ページ間で CSS を使い回せなくなり、各ページが少し重くなります。

    どれを選ぶか

    状況向いている案
    CSS が数十 KB 以上ある／ページ数が多い案2（内容ハッシュ）
    CSS が数 KB 程度／ページ数が少ない案3（埋め込み）
    ビルド工程を持てない案1でしのぐ（期間を数分に）

    このサイトは最終的に案3にしました。 スタイルシートが圧縮後 6KB 程度と小さく、ページも十数枚しかないので、 使い回せない不利より、事故が構造的に起きなくなる利点が勝ると判断したためです。 表示速度の面でも、外部ファイルへの往復が1つ減ります。

    元のスタイルシートは1枚のまま残し、 公開用のファイルを作るときにコメントを落として各ページへ流し込む形にしました。 編集するのは従来どおり1枚なので、手間は増えていません。

    一般化すると

    今回の教訓は、CSS に限った話ではありません。

    HTML と、そこから読むファイルの寿命が違うと、いつか噛み合わなくなる。 HTML を常に最新にするなら、そこから参照するファイルは 「URL が変われば中身も変わる」状態にしておく。

    JavaScript でも同じことが起きます。むしろ JS のほうが深刻で、 新しい HTML の要素を古いスクリプトが探しにいって、 エラーも出さずにただ動かないという壊れ方をします。 画面が崩れる CSS のほうが、まだ気づきやすいくらいです。

    画像やフォントは中身が変わりにくいので実害は出にくいのですが、 差し替えたときに同じ罠にはまります。ロゴを新しくしたのに古いロゴが出続ける、というやつです。

    まとめ

    • 特定の端末でだけ崩れるときは、環境差ではなく訪問履歴の差を疑う
    • 手元のファイルではなく、実際に配信されているものを取得して確かめる
    • Cache-Control は HTML とサブリソースで別々に設定されている。両方見る
    • 直すのは期間ではなく、同じ URL で中身が変わる状態のほう
    • 小さいサイトなら、埋め込んでしまうのがいちばん確実
