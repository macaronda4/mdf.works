ブラウザで見えるのに fetch で読めない
CORS の制約と確認方法

表示できるデータを別サイトの JavaScript から読めない理由。CORS、no-cors、プリフライト、ヘッダーの制約を整理し、通信エラーを切り分ける確認手順を紹介します。

ブラウザ 2026年8月27日 約7分で読めます

目次

    「表示できる」と「データを読める」の違い

    動画や画像がブラウザに表示されるのに、別のサイトの JavaScript から同じ URL を fetch すると失敗することがあります。これは JavaScript の計算能力の限界ではありません。表示と、取得した内容をプログラムから読み出すことには、異なる条件があるためです。

    ブラウザだけでのファイル保存が一律に不可能なわけではありません。利用者が選んだローカルファイル、同じオリジンのデータ、配信元が CORS で読み取りを許可したデータは処理できます。このサイトの画像ツールも、利用者が選んだファイルをブラウザ内で処理します。

    オリジンは、URL のスキーム・ホスト・ポートの組です。たとえば http://localhost:8000 と http://localhost:8001 は別オリジンです。自分で立てたサーバー同士でも、ポートが違えば今回の確認に使えます。

    過去の試行から言えること、言えないこと

    以前の版では、ある API で status 200 と 199,008 文字の本文が得られ、別の宛先では TypeError: Failed to fetch になったことを根拠に、違いは CORS だけだと説明していました。その結果だけでは原因を断定できません。宛先ごとの DNS・TLS・接続状態や、URL の有効性は別に確認する必要があります。

    特に、実際に利用できる完全な動画配信 URL を確認していない試行から、配信元の CORS 設定を判断することはできません。再現条件が揃っていないため、その比較は特定サービスの仕様を示す証拠としては扱いません。以下は Fetch の仕様と MDN の説明に基づいて、原因を切り分ける方法を整理したものです。

    cors と no-cors の結果を分ける

    条件JavaScript から見える結果
    通常の fetch で CORS が許可される許可された応答本文とヘッダーを読み取れる
    通常の fetch で CORS の検査に失敗するPromise が拒否される。opaque な Response が返るわけではない
    no-cors で別オリジンの取得が成功するopaque な Response。status は 0 と見え、本文やヘッダーは読み取れない
    ネットワーク自体に問題があるno-cors でも失敗する場合がある

    no-cors は CORS を突破して本文を読むためのオプションではありません。opaque な応答で本文が空に見えても、サーバーが空のファイルを返したことや、実際の HTTP ステータスが 0 だったことを意味しません。プログラムに情報を公開しない応答です。

    実際に確認するときの順序

    1. 同じオリジンの小さなファイルを用意する自分のページと同じサーバーに text ファイルを置き、URL の間違いや JavaScript の例外を先に取り除きます。
    2. 管理できる別オリジンで比較する別ポートのサーバーで同じ本文を返し、Access-Control-Allow-Origin の有無だけを変えます。比較する URL、ブラウザのバージョン、送ったヘッダーを記録します。
    3. 開発者ツールで通信とエラーを確認するConsole のエラーと Network の要求・応答を照合します。Failed to fetch の文字列だけで CORS と決めないことが大切です。
    4. 読み取り失敗と HTTP エラーを区別する読み取りが許可された応答なら、404 や 500 でも fetch 自体は解決する場合があります。response.ok と status も確認します。
    try {
  const response = await fetch(url);
  console.log(response.type, response.status, response.ok);
  const text = await response.text();
  console.log(text.length);
} catch (error) {
  console.error(error);
  // Console と Network で原因を確認する。
}

    この例は読み取り結果を調べるものです。ログインが必要なサービスの状態や、署名付き URL の期限まで検証するものではありません。自分で管理するテスト用データを使えば、認証や配信元固有の事情を切り離して確認できます。

    実際の要求が送られる前に止まることもある

    CORS は応答の読み取りを制御しますが、「要求は必ず送られる」とも言えません。条件によってはブラウザが先に OPTIONS のプリフライト要求を送り、メソッドやヘッダーが許可されるか確認します。プリフライトに失敗すれば、本来送りたかった要求は送信されません。

    一方、プリフライトの要らない要求は、サーバーに届いてから応答の読み取りだけが拒否される場合があります。したがって CORS だけを、操作の実行を防ぐ仕組みとして使うこともできません。サーバー側の認証・認可や CSRF 対策は別に必要です。

    ヘッダーはどこまで設定できるか

    ブラウザには、ページのスクリプトから自由に設定できないヘッダーがあります。ただし「Origin・Referer・User-Agent・Cookie の4つだけが、必ず書き換わる」という説明は正確ではありません。

    ヘッダー確認したい点
    Origin / Cookie通常のページでは fetch の headers に任意の値を設定できない。ブラウザが管理する
    Refererheaders への直接指定には制限がある。一方、referrer や referrerPolicy オプションで仕様の範囲内の制御ができる
    User-Agent現在の仕様では禁止ヘッダー一覧から外れている。ただし MDN は Chrome の fetch が指定値を落とす実装上の挙動を説明している
    独自の X- ヘッダー設定できても、別オリジンへの要求ではプリフライトと配信元の許可が必要になる場合がある

    禁止対象はこの表だけではありません。最新の一覧は MDN と Fetch 標準で確認できます。また、User-Agent や Referer の値を変更できる環境でも、それだけでブラウザの CORS 判定を無効化できるわけではありません。

    動画サイト自身のページと条件が違う理由

    同じオリジンからの取得、配信元が許可した別オリジンからの取得、メディア要素での再生は、それぞれ条件が異なります。別ドメインの動画が再生されたことから「その配信元はすべてのページの fetch を許可している」とも、「特定のオリジンだけ許可している」とも断定できません。実際の配信方式と応答を確認する必要があります。

    さらに、認証・URL の期限・コンテンツ保護など、CORS 以外の条件もあります。CORS の許可だけであらゆる動画を保存できるわけではなく、再生できたことも再利用の許可を示すものではありません。

    言語を変えると解決するか

    JavaScript でも WebAssembly でも、ブラウザの fetch を使う部分には同じ制約があります。ファイル形式の変換などの計算を移植できても、配信元から読み取る許可がない問題は別です。逆に、読み取れる入力であれば、ブラウザ内の変換は十分に可能です。

    拡張機能やサーバー上のプログラムは、通常のページとは権限や実行環境が違います。拡張機能の場合も、許可されたホストやコードの実行場所によって挙動が変わります。詳しくは拡張機能の権限の見かたを参照してください。

    この区別が守っているもの

    見知らぬサイトが、利用者の社内システムやメールの応答を自由に読める状態は困ります。Cookie の送信には fetch の credentials 設定、SameSite、ブラウザの第三者 Cookie 制限なども関わるため、「ログインしたタブがあると常に認証情報が付く」わけではありません。それでも、別オリジンの応答を誰に読ませるかを制御する意味は変わりません。

    通信の失敗を調べるときは、まず同じ条件で再現し、次に Network と Console を見る。そのうえで、読み取り許可の問題なのか、接続や認証の問題なのかを分ける。この順序なら、言語の移植やヘッダーの変更を試す前に、必要な対策を絞れます。
