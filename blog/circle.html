画像から円を検出する
ハフ変換だけでは足りなかった話

スクリーンショットの中の丸いアイコンを、ブラウザだけで自動的に見つける。 Kuroko の中核にある処理です。 教科書どおりに実装した最初の版は、合成した練習用の画像で 16個中1個しか見つけられませんでした。 候補を出すことは簡単で、本物かどうかを決めることが難しいという話をします。

開発 2026年8月22日 約8分で読めます

目次

    やりたかったこと

    チャットのスクリーンショットには、丸いアイコンが縦に並びます。 これを自動で見つけて隠したい。制約は2つありました。

    • 画像を外に出さない。処理はすべてブラウザの中で完結させる。サーバーに送らないことがこのツールの前提です。
    • 学習済みモデルを使わない。数MBのモデルを読み込むと、ページを開いた瞬間に使える手軽さが失われます。

    つまり、古典的な画像処理だけで解くということです。 幸い「円を見つける」には確立した方法があります。ハフ変換です。

    ハフ変換：総当たりを賢くやる

    素朴に考えると、円を探すには「中心の位置」と「半径」の組み合わせを すべて試すことになります。画像が 1000×1000 で半径が 10〜100 なら、 1000 × 1000 × 90 通り。これは重すぎます。

    ハフ変換の発想は逆向きです。候補を試すのではなく、輪郭の点に投票させます。

    1. 輪郭を取り出す 隣り合うピクセルの明るさの差（勾配）が大きいところが、輪郭です。
    2. 各点が「中心はこのへんだ」と投票する 投票先を集計する配列を用意して、票を足していきます。
    3. 票が集中した場所が中心 円周上の点はすべて同じ点を指すので、そこだけ票が突出します。

    勾配の向きを使うと、一気に軽くなる

    素朴なハフ変換では、1つの輪郭点が「あり得る中心」すべてに投票します。 半径が未知なら、その点を中心とする円全体が投票先です。これでも重い。

    ここで使えるのが、輪郭には向きがあるという性質です。 円周上の点では、明るさの変化する方向が必ず中心を向いています。 だから、その線上だけに投票すればよい。 

    // 勾配（Sobel）の向きに沿って投票する
const gx = ..., gy = ...;            // その点の勾配
const len = Math.hypot(gx, gy);
if (len < EDGE_MIN) continue;        // 弱い輪郭は無視

const ux = gx / len, uy = gy / len;  // 中心を向く単位ベクトル
for (let r = R_MIN; r <= R_MAX; r++) {
  // 内側と外側の両方に投票する（明暗どちらの円か分からないため）
  vote(x - ux * r, y - uy * r);
  vote(x + ux * r, y + uy * r);
}

    投票先が面から線に減るので、計算量が桁で変わります。 さらに投票用の配列を半分の解像度で持てば、票が集まりやすくなり、 メモリも4分の1で済みます。

    ここまでは順調でした。中心の候補は、実際きれいに出ます。

    そして、16個中1個

    候補が出たら、次はそれぞれが本当に円かを判定します。 最初に書いたのは素直な方法でした。

    円周被覆率。推定した円周上を等間隔にたどり、 そこに輪郭がある割合を数える。8割あれば円だろう、と。

    練習用に作った合成画像（背景の上にアイコンを並べただけのもの）で試したところ、 16個のうち1個しか通りませんでした。 通らなかったのではなく、正確には間違ったものが大量に通った結果、 本物が埋もれていました。

    原因はこうでした。 被覆率は「円周上に輪郭があるか」しか見ていません。 ところが文字が詰まった領域は、どこを通っても輪郭にぶつかります。 半径をいろいろ変えれば、そのうちどれかが高得点を出す。 「輪郭が多い場所」を「円」と取り違えていたわけです。

    手当て1：外側が静かであることも要求する

    本物のアイコンには、被覆率だけでは表せない特徴があります。 円の外側が平坦で、しかも境界をまたぐと色が段差状に変わることです。 これを別の得点として計算し、2つを組み合わせました。 

    // 円周の被覆率と、外周の「静かさ＋段差」を別々に測り
// 低いほうを採用する（両方を満たすものだけが残る）
const score = Math.min(coverage, ringScore);

    平均ではなく min にしたのが要点です。 平均だと、片方が突出していればもう片方の低さを埋めてしまいます。 文字だらけの領域は被覆率こそ高くても、外周が静かではないので落ちる。 2つの独立した条件を同時に要求すると、偽物は急に通らなくなります。

    これで合成画像は 16 個すべて検出できるようになりました。 問題は、ここからでした。

    実際のスクリーンショットで、11個中0個

    手元の実際のスマートフォンのスクリーンショットに掛けたところ、 1個も見つかりませんでした。合成画像で満点なのにです。

    調べていくと、原因は判定そのものではなく、 その手前に置いていた足切りの条件でした。 「候補の周囲とどれだけ差があるか」を測って、差が小さいものを先に捨てていたのです。

    合成画像では、この値がだいたい 0.45 以上ありました。だから 0.45 を境目にした。 ところが実物では 0.25 しかありませんでした。 明るいアイコンが、単色に近い背景に載っていたためです。

    ここが今回いちばんの反省点です。 しきい値の 0.45 は、測って決めた「正しい値」のつもりでした。 実際には自分が作った練習用画像の性質を、そのまま数値にしていただけでした。 合成データで調整したしきい値は、暗黙の前提ごと固定されます。 そして前提が外れていることは、実データを通すまで分かりません。

    この足切りは廃止し、半径の推定は勾配の分布から求める方式に置き換えました。 判定は前述の min(coverage, ring) に一本化しています。

    そもそも輪郭が無い場合

    次に当たったのが、装飾フレームです。 アイコンの周りに飾り枠を付けられる機能があり、これが付くと 円の輪郭そのものが存在しません。 探すべき形が無いので、ハフ変換には原理的に見つけられません。

    ここで方針を変えました。輪郭を探すのをやめました。

    1. 背景色を決める その行の帯全体で最も多く出現する色を背景とします。
    2. 列ごとに、背景でないピクセルの割合を数える アイコンがある列は、上から下まで背景以外で埋まります。
    3. その割合が高い列が続く範囲を、横幅とする アイコンの左端と右端が、これで決まります。
    4. 縦方向にたどって上下端を決める 背景の行が2行続いたら、そこで終わりと判断します。

    形を仮定しない代わりに、「背景ではない塊がそこにある」という 弱い事実だけを使います。飾り枠が付いていても、この事実は変わりません。

    背景色の取りかたで一度壊した

    この方式は背景色が命です。最初は左上あたりを参照していました。 ところが、そこがちょうど飾り枠の内側に入ってしまい、 背景を [227, 240, 253]、つまりほぼ白と判定していました。

    背景が間違っていると、そこから先の処理がすべて狂います。 「背景でないピクセル」の定義が壊れるからです。 画面の端を1点だけ見るのをやめ、行の帯全体の最頻色を使うようにしました。 左右にパネルが分かれた画面でも、背景に濃淡があっても、これなら効きます。

    動かなかった原因が、2ピクセルだったこと

    小さいアイコンだけがどうしても見つからない、という症状が残っていました。 判定を緩めても改善しません。

    原因は、投票用の配列を半分の解像度で持っていたことに対する、 座標の戻しかたの間違いでした。ずれは2ピクセルです。 

    // 誤り：半分の格子から元の座標に戻すときに 2px ずれていた
const cx = xx * 2 + 3 - 2;

// 正しい：格子の中心を指す
const cx = (xx + 1) * 2 + 1;

    大きいアイコンでは、2ピクセルのずれは判定の誤差に吸収されます。 半径 15 ピクセル程度のアイコンでは、吸収されません。 「アルゴリズムが悪い」と思って何時間も式をいじっていた対象が、 実際には座標の変換式だったということです。

    教訓として残しているもの： 画像処理で結果がおかしいとき、疑う順番は ①座標の対応 ②境界の扱い ③しきい値 ④アルゴリズム。 この順です。実感として、上の2つが原因であることのほうが多いです。

    最終的な結果

    同じ画像を Python に移植して、正解を数えながら詰めました。 ブラウザ上でログを見るより、はるかに速く回せます。

    対象最初の版最終
    合成画像（明・暗・JPEG・縮小の4種）16個中1個すべて検出
    スマートフォンのスクリーンショット11個中0個11個中11個
    返信プレビューを含む画面—8個中8個（返信2件の判別も含む）

    この作業から持ち帰ったこと

    • 見つけることより、確かめることのほうが難しい。候補の生成は教科書どおりで足ります。手間の大半は、偽物を落とす側に掛かりました。
    • 独立した2つの条件の min を取ると、偽物が急に落ちる。1つの指標を厳しくするより効きます。
    • 合成データで決めたしきい値は、前提ごと固定される。実データを通すまで、その前提には気づけません。
    • 探している形が無いなら、形を探すのをやめる。より弱い、しかし壊れにくい事実に乗り換えるほうが確実です。
    • まず座標を疑う。2ピクセルで結果は変わります。

    実際の動きは ツール で確認できます。 画像はブラウザから出ないので、手元のスクリーンショットでそのまま試せます。 うまく検出されない画像があれば、お問い合わせから教えてください。
